# OPT-SCH-001 — Разделение ранжирования пользователей и аллокации ресурсов (вынос аллокаторов в отдельный модуль)

> Тип: OPT | Модуль: SCH | Ответственный: Тимур (Scheduler) | База: `dev@ae9db40`  
> Статус: черновик спецификации к планёрке 2026-10-17 
> Связанные документы: карточка в [features.md](../features.md) (§1, OPT-SCH-001), TO-BE-схема в [diagrams.md §3](../diagrams.md), наблюдения [audit.md](../audit.md) (DOC-SCH-002 — устаревшие docstring, правятся тем же MR; BUG-SCH-008 — состояние тестового набора)

## 1. Цель

Устранить слияние двух разных задач в классах планировщиков — **ранжирования** (кому и в каком порядке давать ресурс) и **аллокации** (какие именно RBG занять под грант) — и вынести аллокаторы в отдельный модуль. Сейчас механика аллокации (`remaining_buffer`, вызов `ALLOCATE_RBG`, сборка индексов RB, условия прерывания цикла) частично продублирована в шести `_allocate_pdsch` (`SCHEDULER.py` :1901, :2010, :2130, :2239, :2393, :2601): новый алгоритм требует копирования общего кода, этапы нельзя заменить или протестировать по отдельности. Открытый PR #39 добавляет ещё два класса с собственными `_allocate_pdsch`, ветка `feature/drl-scheduler` уже оперирует понятием «ranker» — стоимость дублирования растёт.

## 2. Входит / не входит

**Входит:** интерфейсы `UserRanker`/`ResourceAllocator`; реализации `TDGreedyAllocator`, `RRCyclicAllocator`, `FDPerRBGAllocator` (критерий выбора UE на RBG — подставляемая стратегия); ранжировщики BestCQI/PF/RR; фабрика пар с обратной совместимостью имён (`'BestCQI'`, `'ProportionalFair'`, `'RoundRobin'`, `'FD_BCQI'`, `'FD_FGS'`, `'FD_PF'`); вынос аллокаторов и ранжировщиков в отдельные файлы модуля (`ALLOCATORS.py`, `RANKERS.py` — имена фиксируются на шаге 2); регрессионные сценарии; правка устаревших docstring (DOC-SCH-002).

**Не входит:** изменение поведения алгоритмов (метрики и порядки выбора сохраняются); таблицы TBS (FEAT-SCH-002); откат контроля `release_cce` (FEAT-SCH-001); позиции CCE (FEAT-SCH-007); расслоение buffer processing (OPT-SCH-007); правки любых файлов вне зоны Scheduler (`SIMULATION_MANAGER.py`, `UE_MODULE.py`, `BS_MODULE.py`, `RES_GRID.py`) — только запросы из [features.md §2](../features.md).

## 3. Входы / выходы (контракты, черновик)

```
UserRanker.rank(windowed_ues, ctx) -> priority_list
    ctx: cqi_map, amc, bs_buffer_size, rr_*_offset (для RR-ранжировщиков)
    контракт: проставить user['priority'] (и user['instant_rate'] для PF), порядок списка = порядок обхода

ResourceAllocator.allocate(tti, ues_with_pdcch, ctx) -> allocation: {UE_ID: [freq_idx]}
    ctx: lte_grid, amc, bs_buffer_size, sb/wb cqi-доступ через cqi_map
    контракт: инициализировать allocation для всех eligible UE; учитывать remaining_buffer;
              занимать RBG только через lte_grid.ALLOCATE_RBG (атомарно с откатом)

ResourceAllocator.rollback(ue_id) -> None   # точка встраивания для FEAT-SCH-001, сейчас no-op
```

Фабрика: `SchedulerInterface.create(name, lte_grid, bs, **kwargs)` продолжает принимать прежние имена и отображает их на пары (ranker, allocator); новые пары адресуемы явно (`create('custom', ..., ranker=..., allocator=...)` — форма фиксируется на шаге 2). Совместимость с `SchedulerConfig` (SIMULATION_MANAGER.py:871) сохраняется без правок SM: прежние строки алгоритма работают как раньше.

## 4. Ошибки и граничные случаи

- Неизвестное имя алгоритма в фабрике — `ValueError` с перечнем допустимых (текущее поведение :264 сохраняется).
- Пустой `windowed_ues` — ранжировщик возвращает пустой список; оркестратор уходит в `_empty_result` (:1007) без изменений.
- Пустой `ues_with_pdcch` — аллокатор возвращает allocation с пустыми списками для всех eligible (текущий контракт `_allocate_pdsch`).
- Отказ `ALLOCATE_RBG` (RBG занят) — откат группы через `RELEASE_RBG` и пропуск RBG (текущее поведение сохраняется).
- CQI = 0 у кандидата внутри FD-цикла — пропуск пользователя (как сейчас :2637); латентный крах этапа 7 (BUG-SCH-007) этой спецификацией **не** лечится — отдельная карточка.
- Нарушение контракта ctx (отсутствующий ключ) — явный `KeyError`/`ValueError` с именем поля; форма выбирается на шаге 2 и фиксируется в docstring интерфейсов.

## 5. Зависимости

- **BUG-SCH-008** (тестовый набор неработоспособен на `dev`): регрессионная приёмка до восстановления набора идёт золотыми сценариями (п. 6); восстановление запрошено у автора модуля/владельца репозитория ([features.md §2](../features.md)) и не входит в эту работу.
- **PR #39** (QoS-планировщики, +468 строк в `SCHEDULER.py`): порядок слияния согласовать с автором PR — рефакторинг до или после, чтобы не переносить два новых `_allocate_pdsch` дважды.
- **PR #33** (`GridInterface`): облегчает передачу сетки в аллокатор интерфейсом, но не требуется; контракт `ALLOCATE_RBG/GET_RBG_*` не меняется.
- DOC-SCH-002: правка устаревших docstring идёт тем же MR (иначе после выноса аллокации они станут неверны дважды).

## 6. Способ проверки

1. Золотой TD-сценарий ([README §4](../../README.md)): после рефакторинга результат побитово тот же — `allocation = {1: [6..17], 2: [], 3: [0..5]}`, `pdcch_ue_cce_allocations = {3: 1, 1: 1}`, извлечено 8004/2404 бита, EWMA 16008/4808. Сценарий фиксируется как автотест **до** начала рефакторинга.
2. FD-сценарий: пер-RBG выбор по контрастным SB CQI (fallback на WB при пустом списке) — распределение и числа `amc.get_stats()` совпадают с дореформенными.
3. RR-сценарий: ротация `rr_ue_offset`/`rr_rbg_offset` между соседними TTI совпадает с дореформенной.
4. Демонстрация независимости: отсутствующий алгоритм (FD_RR — round-robin в частотной области) добавляется новыми классами ranker+allocator **без правок оркестратора и фабрики-пары**.
5. Если к моменту MR набор восстановлен автором (BUG-SCH-008): `python3 -m pytest tests/scheduler_tests/ -q` из `PyScheduler/` — без изменения ожиданий.

## 7. Критерий готовности

- Все сценарии п. 6 совпадают с зафиксированными дореформенными значениями.
- В `SCHEDULER.py` не осталось тел аллокаторов: шесть `_allocate_pdsch` сведены к выбору стратегии; дублирование механики RBG-цикла устранено (grep по `ALLOCATE_RBG` в рантайм-коде даёт одну точку в базовом аллокаторе).
- Фабрика принимает прежние имена; `SchedulerConfig` и вызов в SIMULATION_MANAGER (:1196) не правились.
- Docstring приведены в соответствие коду (DOC-SCH-002 закрыт).
- MR самодостаточен: описание содержит ссылку на эту спецификацию и таблицу «старое поведение → новое поведение» по каждому алгоритму.

## 8. Требуемый MR

- Ветка: `opt/SCH-001-ranker-allocator` от `dev@ae9db40`; MR в `dev`.
- Файлы: `PyScheduler/SCHEDULER.py` (оркестратор + фабрика), новые `PyScheduler/ALLOCATORS.py`, `PyScheduler/RANKERS.py` (имена по шагу 2), тесты-сценарии п. 6, документы модуля (`PyScheduler/scheduler/`: README §5, diagrams §3→AS-IS после слияния, features-статусы).
- Не трогать: другие модули, CI, тестовую инфраструктуру (BUG-SCH-008 — отдельный MR автора модуля).
- Ревью: автор модуля + автор PR #39 (порядок слияния).

## 9. План реализации

1. Инвентаризация: выписать общую и особенную части шести `_allocate_pdsch` (+ классы PR #39 по состоянию на момент слияния).
2. Черновик интерфейсов и имён файлов; ревью с автором модуля; фиксация формы ошибок (п. 4).
3. `TDGreedyAllocator` + ранжировщики BestCQI/PF; перевод двух TD-классов; прогон сценариев 1 и 3.
4. `RRCyclicAllocator`; перевод RR; прогон сценария 3.
5. `FDPerRBGAllocator` с подставляемым критерием; перевод трёх FD; прогон сценария 2.
6. Фабрика пар + совместимость имён; демонстрация п. 6.4.
7. Правка docstring (DOC-SCH-002), актуализация документов, MR.

## 10. Риски

- Дрейф поведения при рефакторинге — митигация: сценарии п. 6 фиксируются до старта и прогоняются после каждого шага 3–6.
- Конфликт с PR #39 по порядку слияния — митигация: согласование до шага 1; при слиянии PR #39 первым — его два класса переводятся на интерфейсы тем же MR.
- Гранулярность интерфейса (точечные коммиты RBG против объекта-маски): маска как результат не вводится (DCI/AllocationTracker — OPT-SCH-007).
