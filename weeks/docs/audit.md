## 2. Карточки наблюдений

### BUG-SCH-001 — Двойное нулевое обновление throughput у незапланированного UE
- **Объект:** `PyScheduler/SCHEDULER.py::SchedulerInterface._process_buffers` (:874; ветки :905–906 и :925–926)
- **Категория:** подозрение на баг
- **Наблюдение:** UE без выделенных RB, но с живым буфером получает `UPD_DL_THROUGHPUT_BPS(0)` дважды за TTI: ветка `allocated_rbs == 0` (:905) не делает `continue`, затем срабатывает ветка `max_bytes <= 0` (:925). Аналогично UE без буфера: :906 + :912.
- **Доказательство:** замер на `ae9db40`: сценарий README §4, у UE2 заранее выставлен `average_throughput = 1 000 000`; инструментированный счётчик вызовов — `UE2: 2 вызова UPD(0)`; результат `average_throughput = 996 004 = 1e6·(1−0.002)²` вместо `998 000 = 1e6·(1−0.002)`.
- **Влияние:** EWMA-среднее незапланированных UE затухает вдвое быстрее — знаменатель PF-метрики (`_calculate_priorities` :2088) «остывает» некорректно; на длинных прогонах искажает справедливость PF/FD_PF.
- **Как проверить:** воспроизвести замер выше; уточнить у владельца модуля: двойной шаг — намеренное «остывание» или пропущенный `continue` в ветке :905.
- **Статус:** подтверждено замером
- **Связь:** issue пока нет; учесть в FEAT-SCH-005 (PF)

### BUG-SCH-002 — Невалидный CQI не затирает устаревшую запись карты
- **Объект:** `PyScheduler/SCHEDULER.py::SchedulerInterface._refresh_cqi` (:498; WB-ветка :521–535, SB-ветка :540–547)
- **Категория:** вопрос
- **Наблюдение:** CQI вне [1..15] игнорируется — существующая запись `cqi_map` сохраняет старое значение без ограничения по возрасту; пустой `sbb_cqi` старое значение также не очищает. Метки `last_wb_update`/`last_sb_update` пишутся, но нигде не проверяются на устаревание.
- **Доказательство:** чтение кода :521–547; docstring «Invalid CQI (вне [1-15]) игнорируются» (:512).
- **Влияние:** при прекращении отчётов UE планируется по последнему корректному CQI неограниченно долго; в реальной сети периодичность отчётов задаётся CQI-ReportConfig (TS 36.331), у нас интервалы `wb/sb_cqi_upd_interval` (:330–331) есть, а контроля свежести нет.
- **Как проверить:** уточнить у владельца модуля: модель «последний валидный отчёт» — намеренная? Если да — нужен ли параметр максимального возраста записи. Настройка отчётности CQI уже запрошена в issue #28.
- **Статус:** подтверждено (факт в коде); баг/не баг — оценивает владелец модуля
- **Связь:** issue #28 (настройка CQIReport)

### BUG-SCH-003 — FD-алгоритмы выбирают по SB CQI, а ёмкость гранта считается по WB
- **Объект:** FD `_allocate_pdsch` (FD_BCQI :2239, FD_FGS :2393, FD_PF :2601 — SB-выбор :2631–2637) vs `_process_buffers` (:915 — `cqi = self._get_wb_cqi(ueid)`)
- **Категория:** вопрос (рассогласование модели)
- **Наблюдение:** на этапе 6 FD-планировщики выбирают победителя по SB CQI конкретного RBG, на этапе 7 вместимость выделенного считается по WB CQI.
- **Доказательство:** чтение кода (ссылки выше).
- **Влияние:** UE мог получить RBG именно потому, что его SB CQI на этих участках выше WB, но извлечение из буфера и статистика throughput считаются по WB — оценка и факт расходятся; EWMA-знаменатель PF следующего TTI строится на WB-оценке.
- **Как проверить:** FD-сценарий с контрастными SB CQI: сравнить `dl_capacity_bits_sum_tti` при расчёте по WB и по среднему SB выделенных RBG.
- **Статус:** подтверждено (факт в коде); величина влияния — гипотеза
- **Связь:** FEAT-SCH-002/FEAT-SCH-003; в srsRAN 4G ёмкость считается по среднему CQI выделенной маски (`get_dl_cqi(rbgs)`, `sched_ue_cell.cc:400`)

### BUG-SCH-004 — `_empty_result()` не сбрасывает часть счётчиков статистики
- **Объект:** `PyScheduler/SCHEDULER.py::SchedulerInterface._empty_result` (:1007–1032), `_update_stats` (:1074)
- **Категория:** подозрение на баг
- **Наблюдение:** при досрочном выходе (после этапов 1, 2.5, 4, 5) обнуляются `_last_priority_list_full`, `_last_allocation`, `_last_users` и счётчики eligible/RB/active через `_update_stats(tti, 0, 0, 0)`, но `_last_pdcch_blocked_count` и `_last_avg_priority_value` не трогаются — значения прошлого TTI «залипают» в `get_stats()` (:483–484).
- **Доказательство:** чтение кода :1007–1032 и :1074–1088.
- **Влияние:** метрики пустых TTI недостоверны: по `sch_pdcch_blocked_count`/`sch_avg_priority_value` нельзя отличить «в этом TTI ничего не произошло» от «данные прошлого TTI».
- **Как проверить:** два TTI подряд: полный, затем с пустыми буферами; сравнить поля `get_stats()` до/после.
- **Статус:** подтверждено чтением кода
- **Связь:** пока нет; тривиальный фикс — два сброса в `_empty_result`

### BUG-SCH-005 — `release_cce` — заглушка: CCE «утекают» до конца TTI
- **Объект:** `PyScheduler/SCHEDULER.py::PDCCHManager.release_cce` (:1538)
- **Категория:** долг (осознанный: docstring содержит сценарий применения и пошаговую планируемую логику)
- **Наблюдение:** порядок control-first (этап 5 PDCCH → этап 6 PDSCH) без отката контроля: если после выделения CCE распределение RBG для UE не состоялось, освобождения нет — CCE заняты до `reset_tti()` (:1515) следующего TTI. Для данных откат есть (`RES_GRID::ALLOCATE_RBG` :430 с `RELEASE_RBG` :440), для контроля — заглушка.
- **Доказательство:** код :1538+ («ЗАГЛУШКА для дальнейшей разработки», сценарий «PDCCH выделен, PDSCH не влез»); для сравнения: srsRAN 4G — атомарная транзакция маска+DCI (`sched_grid.cc:134–165`), srsRAN Project — `cancel_last_pdcch` (`pdcch_resource_allocator_impl.cpp:258`).
- **Влияние:** сценарии с дефицитом PDCCH системно искажены: бюджет тратится на гранты, которых не случилось. При малой загрузке мало заметно (сценарий README §4: 2/25 CCE), при экспериментах с малым `max_dl_cce_allowance` или плохим CQI (агрегация 8) — существенно.
- **Как проверить:** искусственный сценарий: малый бюджет CCE + UE, у которого PDSCH заведомо не размещается; сравнить `pdcch_cce_allocated_count` с числом фактических грантов.
- **Статус:** подтверждено
- **Связь:** FEAT-SCH-001

### OPT-SCH-002 — AMC: формула вместо таблиц TBS, сдвиг CQI→MCS, учёт CRS и n_ports
- **Объект:** `PyScheduler/SCHEDULER.py::AdaptiveModulationAndCoding` (`CQI_TO_MCS` :1680, `GET_BITS_PER_RB` :1700, TODO :1718–1723)
- **Категория:** долг (осознанное упрощение с TODO в коде)
- **Наблюдение:** (1) Ёмкость RB считается формулой `RE·Qm·R`; TODO в коде: отклонение от таблиц TBS TS 36.213 §7.1.7.2 ~8–10%, план «CQI → I_MCS → I_TBS → TBS_TABLE». (2) `CQI_TO_MCS` по границам модуляций совпадает с TS 36.213 Table 7.2.3-1, но эффективные спектральности смещены: для CQI 5–13 воспроизводится spec-таблица со сдвигом +2 индекса (код CQI 7 = spec CQI 9: 16QAM 0.601), для CQI 1–4 — удвоенные spec-значения, CQI 14–15 экстраполированы за максимум стандарта → ёмкость систематически завышена (CQI 15: 5.87 против 5.55 bit/RE). (3) Учёт служебных RE в `GET_BITS_PER_RB`: из первого слота вычитается целиком `rs_per_slot = 4·n_ports` (:1711–1712), тогда как половина CRS-символов слота 0 уже исключена вместе с PDCCH-областью через `(7 − pcfich)`; для n_ports=4 линейная формула даёт 16 RE на слот вместо фактических 12.
- **Доказательство:** постатейная сверка `CQI_TO_MCS` (:1680–1695) с TS 36.213 Table 7.2.3-1; TODO :1718; issue #30 (вынесен из ревью PR #26). В ветке `feature/HARQ` (commit `eaf4370`) таблицы размеров TB из 3GPP уже добавлены — ветка не слита (последний коммит май 2026). По пункту (3): замечания о двойном вычитании CRS в слоте 0 и о нелинейности при n_ports=4 сделаны в ревью PR #26; правок и отдельного TODO в коде нет (рядом только пометка про зависимость от CP, :1717).
- **Влияние:** абсолютные значения throughput завышены; сравнение алгоритмов между собой предположительно сохраняется (ошибка систематическая) — гипотеза. Блокирует проверку осуществимости гранта (FEAT-SCH-003) и осмысленный бенчмарк оптимума (FEAT-SCH-004). По пункту (3): при дефолтах (pcfich=2, n_ports=1) код даёт 136 RE/RB против 138 по точному расчёту TS 36.211 §6.10.1 (−1.4%) — ошибка разнонаправлена со сдвигом `CQI_TO_MCS` (+5.6% на CQI 15), что затрудняет интерпретацию абсолютных чисел; при MIMO (n_ports=4) линейное `4·n_ports` завысит overhead.
- **Как проверить:** после перехода на TBS-таблицы сравнить `dl_capacity_bits_sum_tti` на эталонных сценариях (в сценарии README §4 сейчас: 13 848 бит ёмкости, 10 408 извлечено); ручной расчёт RE для (pcfich=2, n_ports=1): slot0 = 84 − 24 (PDCCH) − 2 (CRS символа 4) = 58, slot1 = 84 − 4 = 80, сумма 138 против 136 в коде.
- **Статус:** подтверждено (сверка со spec)
- **Связь:** issue #30; FEAT-SCH-002; ветка `feature/HARQ`; карточка включает бывшее OPT-SCH-002 (учёт CRS/n_ports)

### BUG-SCH-006 — PF: конечный приоритет новичка и «мёртвое» присваивание 1e-6
- **Объект:** `PyScheduler/SCHEDULER.py::ProportionalFairScheduler._calculate_priorities` (:2088; fallback :2104–2107)
- **Категория:** вопрос
- **Наблюдение:** при `avg_throughput <= 0` выполняется `avg_throughput = 1e-6`, но метрика считается как `instant_rate / 1.0` — присваивание 1e-6 на результат не влияет; приоритет новичка конечен. Для сравнения: srsRAN 4G при `R=0` даёт `numeric_limits<float>::max()` (`sched_time_pf.cc:200`) — новичок получает абсолютный приоритет; степень знаменателя `fairness_coeff` настраивается. Ниже (:2117–2122) — закомментированный мёртвый код старой версии метрики.
- **Доказательство:** чтение кода :2104–2122.
- **Влияние:** стартовая динамика PF отличается от промышленной: новые UE не получают приоритетного обслуживания; настраиваемости жёсткости справедливости нет.
- **Как проверить:** сценарий: UE появляется в середине прогона; замерить время до первого обслуживания при текущей метрике и при `priority = max`.
- **Статус:** подтверждено (факт в коде); оценка влияния — гипотеза
- **Связь:** FEAT-SCH-005; roadmap пункт 7 (:2692 «исследование механизма оценки средней пропускной способности для PF»)

### OPT-SCH-004 — Учёт CCE счётчиком: необходимое, но не достаточное условие размещения
- **Объект:** `PyScheduler/SCHEDULER.py::PDCCHManager` (`check_cce_availability` :1435, `allocate_cce` :1466)
- **Категория:** вопрос (осознанное упрощение модели)
- **Наблюдение:** проверяется только остаток бюджета `max_dl_cce − num_assigned_cce`; позиций CCE, поисковых пространств и кандидатов нет. «Осталось 20 CCE» не гарантирует размещение DCI с агрегацией 8: в LTE кандидаты привязаны к search space (TS 36.213 §9.1), srsRAN 4G решает задачу размещения DFS по позициям (`sf_cch_allocator.cc:75`).
