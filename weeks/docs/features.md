## 1. Предложения для своего модуля

### FEAT-001 — Разделить ранжирование пользователей и аллокацию ресурсов
- **Статус:** обсуждается (направление следует из roadmap и дублирования в коде; дизайн — черновик, схема TO-BE в [diagrams.md §3](diagrams.md))
- **Проблема сейчас:** ранжирование (кому) и аллокация (какие блоки) слиты в классах планировщиков; механика аллокации (`remaining_buffer`, `ALLOCATE_RBG`, сборка индексов RB, условия прерывания) частично продублирована в шести `_allocate_pdsch`: жадный TD у BestCQI (:1901) и PF (:2130), циклический у RR (:2010), per-RBG турнир у трёх FD (:2239/:2393/:2601). Новый алгоритм требует копирования общего кода — открытый PR #39 добавляет ещё два класса (`BasicQosAwareScheduler`, `QosAwareScheduler`) с собственными `_allocate_pdsch`; ветка `feature/drl-scheduler` уже оперирует понятием «ranker» (PPO/DQN).
- **Цель:** две самостоятельные сущности с явными интерфейсами — `UserRanker` (порядок/приоритеты UE) и `ResourceAllocator` (выдача RBG); оркестратор этапов не меняется; добавление алгоритма — новая пара стратегий без правок pipeline; дублирование устранено.
- **Предлагаемое изменение:** интерфейсы Ranker/Allocator; общие реализации аллокаторов: `TDGreedyAllocator`, `RRCyclicAllocator`, `FDPerRBGAllocator` (критерий выбора UE на RBG — подставляемая стратегия); фабрика `create()` отображает существующие имена (`'BestCQI'`, …) на пары (ranker, allocator) — обратная совместимость с `SchedulerConfig` (SIMULATION_MANAGER.py:871); QoS-классы из PR #39 и DRL-ranker встают в ту же схему без изменения оркестратора. Размещение — вынос аллокаторов (и ранжировщиков) в отдельный модуль/файлы (например, `ALLOCATORS.py`, `RANKERS.py`) либо отдельные классы внутри `SCHEDULER.py` — решается на этапе черновика интерфейсов (шаг 2); целевой вариант по задаче — отдельный модуль.
- **Входит / не входит:** входит — рефакторинг `SCHEDULER.py`, регрессия, черновик контрактов, правка устаревших docstring (AUD-016); не входит — изменение поведения алгоритмов, TBS-таблицы (FEAT-003), позиции CCE (FEAT-008), правки SIMULATION_MANAGER (отдельный запрос, §2).
- **Входы и выходы:** черновик, не согласован. `Ranker.rank(windowed_ues, ctx) -> priority_list` (ctx: `cqi_map`, AMC, `bs_buffer_size`, RR-offsets); `Allocator.allocate(tti, ues_with_pdcch, ctx) -> {UE_ID: [freq_idx]}` + `rollback(ue_id)` (ctx: `lte_grid`, AMC, буферы). Точка встраивания отката — см. FEAT-002.
- **Зависимости:** регрессионная приёмка — золотые сценарии ([README §4](../README.md), побитово фиксированные числа); тестовый набор модуля сейчас неработоспособен (AUD-015), его восстановление запрошено у автора модуля/репозитория (§2) и не является частью этой работы; порядок слияния с PR #39 (два новых класса — рефакторить их или сначала); `GridInterface` из PR #33 облегчает замену `lte_grid` на интерфейс в контексте аллокатора.
- **Шаги:** 1) инвентаризация дублирования: общая/особенная части шести `_allocate_pdsch` (включая классы PR #39); 2) черновик интерфейсов + TO-BE-схема, ревью; 3) `TDGreedyAllocator` — перевод BestCQI/PF; 4) `RRCyclicAllocator` — перевод RR; 5) `FDPerRBGAllocator` с подставляемым критерием — перевод трёх FD; 6) фабрика пар + совместимость имён; 7) регрессия (см. проверку); 8) правка docstring (AUD-016).
- **Проверка готовности:** минимальный сценарий ([README §4](../README.md)) даёт побитово тот же результат: `allocation = {1: [6..17], 2: [], 3: [0..5]}`, CCE `{3:1, 1:1}`, 8004/2404 бита, EWMA 16008/4808; дополнительно зафиксировать до старта и сравнить после: FD-сценарий (per-RBG выбор по контрастным SB CQI) и RR-сценарий (ротация offsets между TTI); если автор модуля к тому времени восстановит тестовый набор (§2) — и он проходит без изменения ожиданий; демонстрация: отсутствующий алгоритм (например, FD_RR — round-robin в FD) добавляется новыми классами без правок оркестратора.
- **Риски и вопросы:** дрейф поведения при рефакторинге (снижение риска — фиксация контрольных сценариев до начала работ: README §4 + FD/RR-сценарии из проверки готовности); гранулярность интерфейса: точечные коммиты RBG против объекта-маски (маску как результат пока не вводим — DCI/AllocationTracker относятся к FEAT-009); как RR-состояние (`rr_*_offset`) делится между ranker и allocator у FD_FGS; порядок слияния с PR #39.
- **Ссылки:** [diagrams.md §3](diagrams.md); roadmap :2676; AUD-015/016; PR #39; `feature/drl-scheduler`.

### FEAT-002 — Атомарность контроля: реализовать `release_cce` и откат PDCCH при провале PDSCH
- **Статус:** идея
- **Проблема сейчас:** control-first без отката: CCE списываются на этапе 5 (:763) до распределения RBG на этапе 6; `release_cce` (:1538) — заглушка, хотя её docstring содержит и сценарий применения, и пошаговую логику; провал PDSCH после успешного PDCCH оставляет CCE занятыми до `reset_tti()` следующего TTI (AUD-005). Для данных откат есть (`ALLOCATE_RBG`/`RELEASE_RBG`, RES_GRID :430/:440).
- **Цель:** связка PDCCH+PDSCH ведёт себя как транзакция: не разместились данные — контроль возвращается; `pdcch_cce_allocated_count` отражает фактические гранты.
- **Предлагаемое изменение:** реализовать `release_cce(ue_id)` по логике из docstring (проверка выделения → уменьшение `num_assigned_cce` → удаление `cce_allocations[ue_id]` → сброс `user['allocated_cce']`); вызывать в точках отказа аллокаторов, где UE с выделенным PDCCH не получил ни одного RBG (после FEAT-001 — единая точка `Allocator.rollback`). Образец — транзакционность `alloc_dl` в srsRAN 4G (`sched_grid.cc:134–165`); DFS с перестановками истории DCI (`sf_cch_allocator.cc:75`) не перенимаем — до появления позиций CCE (FEAT-008) ему не на чем работать.
- **Входит / не входит:** входит — `PDCCHManager`, точки отказа в TD/FD-аллокаторах, тест на бюджет CCE; не входит — позиции/кандидаты CCE (FEAT-008).
- **Входы и выходы:** `release_cce(ue_id) -> bool` (контракт описан в docstring заглушки).
- **Зависимости:** только внутри модуля; статистика видна наружу через `pdcch_manager.get_stats()` (:1630).
- **Шаги:** 1) реализация `release_cce`; 2) определить точки отказа в каждом аллокаторе (TD: UE не получил RBG; FD: то же); 3) тест: малый `max_dl_cce_allowance` + UE, не помещающийся в RBG → CCE возвращены; 4) сверка `pdcch_cce_allocated_count` с числом непустых allocation в сценарии дефицита.
- **Проверка готовности:** новый тест проходит; в сценарии дефицита контроля `allocated_count == число UE с непустым allocation`; существующие тесты не сломаны.
- **Риски и вопросы:** освобождать ли CCE при частичном выделении (UE получил меньше RBG, чем оценено на этапе 4.5) — обсудить с владельцем модуля; согласовать семантику с будущим HARQ (FEAT-007: ретрансляции резервируют контроль первыми).
- **Ссылки:** AUD-005; roadmap (пункт 3 — «нет нормального DCI»); srsRAN Project `cancel_last_pdcch` (`pdcch_resource_allocator_impl.cpp:258`).

### FEAT-003 — Таблицы TBS TS 36.213 вместо формульной оценки ёмкости
- **Статус:** идея (в коде есть TODO :1718–1723 и issue #30; частичная реализация есть в ветке `feature/HARQ` (commit `eaf4370` — таблицы размеров TB из 3GPP, не слита, последний коммит ветки май 2026))
- **Проблема сейчас:** `GET_BITS_PER_RB` (:1700) — формула RE·Qm·R с отклонением ~8–10% от таблиц TBS (оценка из TODO в коде); `CQI_TO_MCS` (:1680) смещена относительно Table 7.2.3-1 (+2 индекса для CQI 5–13) → ёмкость систематически завышена; учёт CRS в slot0 спорный (AUD-013). FD-цикл не может проверить осуществимость гранта (FEAT-004), бенчмарк оптимума (FEAT-005) без точных байтов малоосмыслен.
- **Цель:** точный расчёт размера TB: CQI → I_MCS → I_TBS → `TBS_TABLE[I_TBS][N_PRB]` (TS 36.213 Table 7.1.7.2.1-1); отклонение от spec = 0; единая точка расчёта на проект.
- **Предлагаемое изменение:** таблицы MCS/TBS в AMC (или в GLOBALS — рядом TODO :1384 «вынести таблицы в GLOBALS»); `GET_BITS_PER_RB` сохранить для быстрой внутренней оценки приоритетов либо заменить во всех четырёх точках потребления (этапы 4.5, 6, 7, статистика AMC) — решить на шаге 2; ревизия ветки `feature/HARQ`: что из `eaf4370`/`bd1fb15` («функции для выбора размеров транспортных блоков») пригодно к переносу.
- **Входит / не входит:** входит — AMC, точки вызова, юнит-тесты на контрольные значения spec; не входит — пересчёт исторических результатов симуляций, реализация HARQ (FEAT-007).
- **Входы и выходы:** `get_tbs_bytes(i_tbs, n_prb) -> int` / `cqi_to_mcs(cqi) -> (modulation, code_rate, i_tbs)` (черновик).
- **Зависимости:** направление транспортных блоков/HARQ (ветка `feature/HARQ`, issue #27): точка расчёта CQI→MCS→TBS должна быть одна на проект; при таблицах TBS ёмкость гранта считать по CQI выделенного набора RBG (как `get_dl_cqi(rbgs)` в srsRAN 4G, `sched_ue_cell.cc:400`) — закрывает AUD-003.
- **Шаги:** 1) ревизия `feature/HARQ@eaf4370` — что переносим; 2) согласовать владельца таблиц (AMC vs TB-модуль) и контракт; 3) реализовать таблицы + тесты по контрольным точкам TS 36.213; 4) заменить потребителей; 5) пересчитать эталонный сценарий ([README §4](../README.md)): зафиксировать новые ожидаемые числа (сейчас: ёмкость 13 848 бит, извлечено 10 408); 6) закрыть AUD-006/AUD-013, отчитаться в issue #30.
- **Проверка готовности:** юнит-тесты на TBS против контрольных значений spec проходят; `dl_capacity_bits_sum_tti` в эталонном сценарии совпадает с ручным расчётом по таблицам.
- **Риски и вопросы:** абсолютные числа throughput изменятся во всех результатах (нужна фиксация «до/после» в описании PR); не сломать FD-метрики (этап 6 использует bits/RB как вес — оставить быструю формулу для метрик или считать таблицы и там).
- **Ссылки:** issue #30; AUD-003/006/013; ветка `feature/HARQ`; TS 36.213 §7.1.7.2, §7.2.3.

### FEAT-004 — Проверка осуществимости гранта в FD-цикле («выбор частот» отдельно от «резервирования»)
- **Статус:** идея
- **Проблема сейчас:** FD-аллокаторы заполняют RBG до исчерпания буфера без проверки «влезет ли запрошенное в выделенное»; оценка ёмкости `r_j_k` используется только внутри метрики (:2643–2647); ёмкость и аллокация живут раздельно (AUD-003). Индикатор FD-режима — эвристика «непустой `sbb_cqi`» (:538–539, TODO заменить на явный флаг; issue #29).
- **Цель:** выбор частот и проверка осуществимости связаны в один цикл (паттерн srsRAN 4G `try_dl_newtx_alloc_greedy`, `sched_base.cc:79`: сначала выбирается маска под потребность UE с пересчётом MCS/TBS, затем резервирование); явный флаг FD в конфигурации.
- **Предлагаемое изменение:** в `FDPerRBGAllocator` (после FEAT-001) — фаза оценки: накопленный набор RBG гранта + пересчёт TBS (FEAT-003) против `bs_buffer_size`; стоп при покрытии потребности; результат — набор RBG (прообраз маски), коммит через существующий `ALLOCATE_RBG`. Флаг `enable_fd` в `SchedulerConfig` вместо эвристики.
- **Входит / не входит:** входит — FD-аллокаторы, флаг FD, тесты; не входит — связность набора под DCI 1A (DCI — заглушка; вернёмся в FEAT-008/009), subband-отчётность на стороне модели канала (запрос в §2).
- **Входы и выходы:** контракт — черновик (набор RBG + TBS на грант).
- **Зависимости:** FEAT-003 (точные байты; без него проверка приблизительная), частично FEAT-001 (точка встраивания); модель канала/UE_MODULE: формат subband-CQI — наш per-RBG список (длина = num_rbg) против subband+индекс+периодичность как в srsRAN 4G (`sb_cqi_info`, K, H=J·K+1); issue #29.
- **Шаги:** 1) синхронизировать FEAT-003 и контракт subband-CQI; 2) прототип на FD_BCQI; 3) сравнение «до/после» на FD-сценарии с контрастными SB CQI (извлечение ≈ потребность, а не «сколько влезло»); 4) распространить на FD_PF/FD_FGS; 5) флаг FD в конфиг.
- **Проверка готовности:** в FD-сценарии извлечённые биты покрывают буфер без систематического перерасхода RBG; существующие FD-тесты проходят.
- **Риски и вопросы:** монотонности TBS по числу PRB при subband нет (комментарий в srsRAN: «one single subband CQI could be dropping the CQI of the whole TB») — пересчёт на каждом шаге; жадность не гарантирует оптимума — измерять через FEAT-005.
- **Ссылки:** issue #29; AUD-003; srsRAN 4G `sched_ue_cell.cc:522` (`find_optimal_rbgmask`), `sched_dl_cqi.h:107` (`get_rbg_cqi`).

### FEAT-006 — PF: fairness_coeff, fast-start для новичков, настройка α EWMA
- **Статус:** идея
- **Проблема сейчас:** знаменатель `average_throughput/1000` (:2110) без настраиваемой жёсткости; новичок получает конечный приоритет `instant_rate/1.0`, присваивание `1e-6` мертвое (:2104–2107, AUD-010); в srsRAN 4G при `R=0` приоритет = `float::max`, степень `fairness_coeff` настраивается (`sched_time_pf.cc:193–200`); α=0.002 захардкожена в двух местах UE_MODULE (:617, :644) с TODO «вывести в управление» — issue #31; двойной нулевой шаг EWMA искажает знаменатель (AUD-001).
- **Цель:** метрика `r / R^fairness_coeff` с настраиваемым коэффициентом и явным fast-start (приоритет новичка — max); α — параметр конфигурации симуляции; одиночный нулевой шаг EWMA для незапланированных UE.
- **Предлагаемое изменение:** параметры в `__init__`/`SchedulerConfig`: `fairness_coeff` (дефолт 1.0 = текущее поведение), `newcomer_boost` (дефолт выкл — чтобы не менять baseline); после FEAT-001 — в `ProportionalFairRanker`; фикс AUD-001 (continue/else в ветке :905); α — на стороне UE_MODULE (запрос в §2).
- **Входит / не входит:** входит — PF/FD_PF-метрика, фикс AUD-001, тесты; не входит — перенос EWMA из UE_MODULE в планировщик, замена схемы сглаживания (roadmap п.7 — отдельное исследование).
- **Входы и выходы:** параметры конфигурации (черновик).
- **Зависимости:** UE_MODULE (α, issue #31); Simulation Manager (проброс параметров в `SchedulerConfig`).
- **Шаги:** 1) фикс AUD-001 отдельным маленьким PR + замер «до/после» (996 004 → 998 000 в repro AUD-001); 2) `fairness_coeff`/fast-start за параметрами; 3) сценарий «UE появляется в середине прогона» — сравнить время до первого обслуживания; 4) запрос к UE_MODULE по α (issue #31).
- **Проверка готовности:** при `fairness_coeff=1.0` и выключенном boost результаты совпадают с baseline (регрессия); при boost новичок обслуживается первым (новый тест).
- **Риски и вопросы:** fast-start может снизить суммарный throughput — фиксировать обе метрики; степень изменения PF-поведения при `fairness_coeff ≠ 1` не исследована — начинать с 1.0.
- **Ссылки:** issue #31; AUD-001/010; roadmap п.7–8 (:2692–2694, защита голодающих UE — fast-start её частичный случай).

### FEAT-007 — HARQ: задействовать поля SchedulingGrant и приоритет ретрансляций
- **Статус:** идея
- **Проблема сейчас:** передача считается успешной по факту выделения; `ndi`, `rv`, `harq_process_id` в гранте (:130–135) не используются; `harq_manager = None` (:335), `_get_harq_retransmissions` (:1201) возвращает пустой список; закомментированные проверки HARQ-процессов в eligibility (:590–592). В обеих srsRAN ретрансляция обслуживается вне очереди метрик (`sched_time_pf.cc:105`, `pending_dl_retxs` в Project).
- **Цель:** минимальная модель HARQ-процессов: пул процессов на UE, приоритет ретрансляции перед новой передачей, реальное заполнение полей гранта.
- **Предлагаемое изменение:** HARQ-менеджер (граница «модуль vs сосед» — решить с TB-направлением); точка встраивания описана TODO самого кода (:1209–1213): вызов `_get_harq_retransmissions` в `schedule()` перед этапом 3, обслуживание в `_allocate_pdsch` с высоким приоритетом; в ветке `feature/HARQ` уже есть создание 8 процессов и проверка статуса (`55a7538`, `282f4ec`) — ревизовать.
- **Входит / не входит:** входит — дизайн и контракт полей, интеграция заглушки; не входит — модель ошибок канала/источник NACK (зона модели канала).
- **Входы и выходы:** контракт — черновик (`harq_manager.get_retransmissions(tti)` уже заявлен в :1222).
- **Зависимости:** TB/HARQ-направление (ветка `feature/HARQ`, issue #27); модель канала (источник NACK); Simulation Manager (такт процессов); FEAT-002 (ретрансляции резервируют контроль — семантика отката).
- **Шаги:** 1) ревизия `feature/HARQ` (5 коммитов, не обновлялась с мая 2026) — переносить или переписывать; 2) согласовать границы: кто владеет процессами, кто — полями гранта; 3) черновик контракта; 4) реализация после FEAT-001 (естественная точка — оркестратор).
- **Проверка готовности:** сценарий с принудительным NACK: ретрансляция обслуживается раньше новых передач, `rv` инкрементируется, `harq_process_id` стабилен между попытками; тесты проходят.
- **Риски и вопросы:** HARQ затрагивает цепочку модулей (UE → BS → Scheduler → Simulation Manager) — без согласования архитектуры не начинать; NDI-семантика требует согласования с TB-направлением.
- **Ссылки:** issue #27; ветка `feature/HARQ`; roadmap (пункт 1: «неизбежно при работе с HARQ» — про вынос buffer processing).

### FEAT-005 — Венгерский метод как офлайн-бенчмарк верхней границы
- **Статус:** идея (исследование; roadmap п.6 :2691 «Исследование механизма распределения RBG, венгерский, жадный и др.»)
- **Проблема сейчас:** все аллокаторы жадные (и наши, и srsRAN — в 4G комментарий к `find_optimal_rbgmask` прямо признаёт отсутствие гарантии оптимальности); цену жадности нечем измерить; пункт 6 роадмапа без такого измерения не закрывается.
- **Цель:** офлайн-эталон: оптимальное назначение UE×RBG (задача назначения, O(N³)) и метрика «процент от оптимума» для любого жадного аллокатора.
- **Предлагаемое изменение:** отдельный исследовательский скрипт (не часть рантайма): вход — матрица `sb_cqi[ue][rbg]` из `CQIMap`, стоимость `a[k][n] = 15 − CQI[k][n]` (минимизация стоимости эквивалентна максимизации суммы CQI); выход — оптимальное назначение и сумма CQI; сравнение на эталонных сценариях трёх подходов: наш per-RBG greedy, greedy в стиле srsRAN 4G (очередь UE + маска каждому), оптимум. Контрольный пример: матрица 4×4, где жадный обход даёт 48 против оптимума 50 (потеря 4% уже на 4×4).
- **Входит / не входит:** входит — бенчмарк-скрипт (рядом с `FD_benchmark.py`), отчёт сравнения; не входит — онлайн-аллокатор: учебная постановка «1 UE — 1 RBG» игнорирует многорыговость гранта, TBS-связность маски и меж-TTI динамику PF.
- **Входы и выходы:** `benchmark(scenario) -> {algorithm: {sum_cqi, pct_of_optimum, fairness}}` (черновик).
- **Зависимости:** направление srsRAN/алгоритмов аллокации — согласование постановки и референса; желательно FEAT-003 (точные байты) и FEAT-004 (сопоставимые жадные стратегии); для fairness-метрики — тестовый модуль (Jain's Index).
- **Шаги:** 1) согласовать постановку (учебная матрица CQI против полной целевой функции с буферами); 2) реализовать офлайн-решатель (`scipy.optimize.linear_sum_assignment` или вручную — по итогам шага 1); 3) прогнать три подхода на эталонных сценариях; 4) оформить вывод «процент от оптимума» как штатную метрику FD-аллокаторов.
- **Проверка готовности:** на контрольной матрице 4×4 бенчмарк воспроизводит 50 (оптимум) и 48 (жадный); отчёт приложен к материалам модуля.
- **Риски и вопросы:** прямоугольное расширение (UE-слоты × RBG) размывает оптимальность — интерпретировать осторожно; `scipy` — новая зависимость? (в проекте уже используется numpy).
- **Ссылки:** roadmap п.6; srsRAN 4G `sched_ue_cell.cc:522`; `FD_benchmark.py` (существующий harness).

### FEAT-009 — Расслоение модуля: buffer processing → BufferManager, каноничный output, уход от прямой записи в RES_GRID
- **Статус:** черновик (roadmap п.1–3 :2676–2686; крупная архитектурная работа)
- **Проблема сейчас:** планировщик и решает, и исполняет: сам извлекает пакеты (этап 7, :874) и сам обновляет статистику UE (:629 через UE_MODULE); возврат `schedule()` вызывающим кодом отбрасывается (:1289), `statistics` всегда пуст (:1000), TODO у `_build_result` (:1005) — «метод будет преобразован или полностью убран» (AUD-012); этап 7 существует потому, что отдельного MAC-слоя в модели нет; roadmap: «Обрабатывать буфер — это не задача scheduler; неизбежно при работе с HARQ; решение — BufferManager», «избавиться от связи с RES_GRID → DCI и AllocationTracker».
- **Цель:** планировщик возвращает гранты (каноничный output: ue_id, RBG-набор, MCS/TBS, HARQ-поля — по образцу srsRAN 4G, где планировщик отдаёт MAC список грантов, `mac.cc:673`); извлечение данных и статистику выполняет соседний модуль; занятие сетки — через DCI/AllocationTracker, а не прямыми вызовами `ALLOCATE_RBG`.
- **Предлагаемое изменение:** поэтапно: (a) зафиксировать каноничную структуру результата и начать потреблять её в SIMULATION_MANAGER; (b) вынести `_process_buffers`/`_logical_channel_multiplexing` в BufferManager (BS_MODULE: `LayeredBufferManager` :1113 уже владеет данными — естественный хозяин); (c) LCP с приоритетами и Bj (TS 36.321 §5.4.3): поля `priority`/`qci` в `BufferStatus` (BS_MODULE :48–49) уже есть, но не используются — территория PR #39; (d) переход RES_GRID → AllocationTracker с учётом `GridInterface` из PR #33.
- **Входит / не входит:** входит — дизайн и контракты; не входит — реализация до завершения FEAT-001/002/003 и согласования с владельцами смежных модулей.
- **Входы и выходы:** контракт гранта — черновик (ue_id, rbg-набор/маска, mcs, tbs, ndi/rv/harq_process_id).
- **Зависимости:** Simulation Manager (потребление результата, StatsManager — issue #23); BS_MODULE (BufferManager, issue #22 — рассинхронизация при отключении UE, issue #25 — кэширование BufferStatus); TB/HARQ-направление (поля гранта, issue #27); RES_GRID (PR #33); issue #35 (разделение проекта на модули).
- **Шаги:** 1) после FEAT-001/002/003 собрать контракт гранта; 2) согласовать с Simulation Manager переход на потребление возврата; 3) пилот: буферная обработка вне планировщика на эталонном сценарии; 4) полная миграция.
- **Проверка готовности:** эталонный сценарий (README §4) проходит с извлечением на стороне BufferManager, результаты идентичны текущим; `statistics` в возврате заполнен и потребляется.
- **Риски и вопросы:** крупнейшая фича модуля — декомпозировать после сборки общей карты развития; до этого держать черновиком; порядок слияния PR #33/#39 влияет на шаги (a) и (c).
- **Ссылки:** roadmap :2676–2686; issues #22/#23/#25/#27/#35; PR #33/#39; AUD-009/012.

### FEAT-008 — Позиции CCE: таблица кандидатов поисковых пространств
- **Статус:** идея (низкий приоритет)
- **Проблема сейчас:** счётчик CCE проверяет только необходимое условие размещения (AUD-011): «осталось 20 CCE» не означает, что DCI с агрегацией 8 найдёт позицию; уровней агрегации как объектов нет — `cce_count` передаётся, но позиций за ним нет.
- **Цель:** хотя бы общее поисковое пространство: кандидаты по уровням агрегации {1,2,4,8} (TS 36.213 §9.1), размещение позициями, отказ при отсутствии кандидата.
- **Предлагаемое изменение:** в `PDCCHManager` — таблица кандидатов и учёт занятых позиций вместо чистого счётчика; DFS с перестановками истории DCI из srsRAN 4G не перенимаем до появления реальной потребности.
- **Входит / не входит:** входит — PDCCHManager, тесты бюджета; не входит — UE-specific search space с хешированием Y_k (отдельное решение).
- **Входы и выходы:** `allocate_cce(ue_id, level) -> позиции | отказ` (черновик).
- **Зависимости:** FEAT-002 (откат по позициям).
- **Шаги:** 1) после FEAT-002; 2) таблица кандидатов CSS; 3) тест: дефицит позиций при формально достаточном счётчике → отказ.
- **Проверка готовности:** тест проходит; `pdcch_stats` отражает размещение позициями.
- **Риски и вопросы:** усложнение без явного заказчика в учебной модели — держать низким приоритетом.
- **Ссылки:** AUD-011; TS 36.213 §9.1; srsRAN 4G `sf_cch_allocator.cc:75`.
